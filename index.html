Many repositories. One openEHR endpoint.

Applications talk to Unio exactly as they would to a single clinical data repository. Unio finds the records across the federation, queries each member in place and returns one answer.

01

A request arrives

An application sends an ordinary openEHR request to Unio, exactly as it would to a single CDR.

02

Identity is resolved

Unio matches the patient centrally and works out which members hold a record. Members that hold nothing are not asked.

03

Members answer in parallel

Each repository is queried over its standard openEHR interface. A slow or unreachable member does not block the others.

04

One result, with provenance

Results are merged in time order and deduplicated. Each entry names its source. If a member could not be reached, the response says so.

ExtensionopenFHIRFHIR R4

The same federation, reached over FHIR

Applications that speak FHIR rather than openEHR get the same federated record. openFHIR sits in front of Unio and exposes a FHIR API. A FHIR query is translated into AQL, Unio runs it across the member repositories, and the merged openEHR result is mapped back into FHIR resources on the way out.

openFHIR is also a SYNTARIC product, so the two are built to work together. Unio joins the openEHR repositories into one record; openFHIR opens that record to the FHIR world, including national exchange platforms and the European Health Data Space. Together they give a federation one openEHR endpoint and one FHIR endpoint, both backed by the same data, with one team behind them.

  • One FHIR endpoint for the whole federation, with no FHIR server at any member
  • One set of mappings, written once in the open FHIR Connect specification
  • Identity resolution, provenance, partial-result flags and audit work exactly as before
  • Members keep running plain openEHR repositories; nothing changes on their side

Built for federations that keep data where it is created

Unio is the shared record for any set of openEHR repositories whose owners keep their own systems: the departments of one institution, the hospitals of a group, or the care organisations of a region. Three capabilities make that work.

Federation gatewayopenEHR RESTAQL

A single openEHR endpoint for the whole federation

The gateway accepts standard openEHR requests, including AQL, and resolves them across the member repositories. Applications do not need to know which organisation holds which record.

  • Existing openEHR applications connect without modification
  • Parallel fan-out with a timeout per member
  • Merged, deduplicated results with the source on every entry

GovernanceMember autonomy

Terms the most cautious member can accept

Data stays with its owner. Care recorded in one system is written to that system's repository and nowhere else. Joining and leaving the federation are configuration changes, and a member that leaves takes nothing away from anyone else.

  • No central copy of clinical data to secure or keep current
  • One ordinary query per request, no bulk extracts, no replication
  • Partial results are declared partial, never presented as complete

Frequently asked questions

The questions programme leads and IT directors ask in the first meeting.

Do we have to replace or migrate our clinical data repository?

No. You keep the repository you have. Unio queries it over the standard openEHR REST API it already supports. Nothing is installed on your side.

Which openEHR repositories does Unio work with?

Any repository that exposes the standard openEHR REST API can be a member. Our demonstration environment federates EHRbase and FerroEHR repositories.

Do our own applications have to change?

No. Applications built against a single openEHR repository work against the federation through Unio without modification. There is no federation-specific API to adopt.

Can applications use FHIR instead of openEHR?

Yes, by putting openFHIR in front of Unio. openFHIR exposes a FHIR API, translates FHIR queries into AQL for the federation and maps the merged openEHR result back into FHIR resources. The member repositories stay plain openEHR and need no FHIR server of their own. openFHIR is also developed by SYNTARIC, so the two products are designed and supported together.

Does Unio store clinical data?

No. Unio keeps only request metadata: counts, statuses, latencies, errors and member URLs. Patient identifiers are replaced before a request is written to the log, and no request or response bodies are stored.

Where does Unio run?

Unio is delivered as a Docker image and runs on Linux. The organisation operating the federation deploys and runs it in the infrastructure of its choice.

What happens when a member is slow or offline?

Each member has its own timeout. A member that does not answer in time is reported as unreachable, the other members' results are returned, and the response is marked as partial. The outage is visible in the operator console.

Can a member leave the federation later?

Yes. Because nothing was copied out of the member's repository, leaving is a configuration change on the gateway. The member's records are already, and only, in its own system.
